# race — 달리기 룰렛 (Race Roulette)

`prelaps.com/race/` 에 들어갈 도구. HTML + three.js.

## 폴더가 이렇게 생긴 이유

```
race/
  ko/index.html      한국어판
  en/index.html      영어판  (hreflang x-default 가 가리키는 곳)
  styles.css
  src/               main · runner · gaits · camera · race · track
                     fx · scenery · labels · hud · entry
  vendor/            three.js 0.185.1 (three.module.min + three.core.min)
```

**도구 루트에 `index.html` 이 없는 건 의도한 것이다.** 헌법 §「주소」 규칙:
언어판은 `/<도구>/<언어>/` 아래 두고 도구 루트는 비워 통로로 쓴다.
루트에 한 언어를 놓으면 그 주소가 그 언어의 canonical 이 되어, 나중에 언어를
추가하려면 canonical 주소를 리다이렉트로 만들어야 한다 — 하면 안 되는 일이다.
`mojibake` 가 한국어를 루트에 둔 상태라 그걸 따라하지 않았다.

`prelaps.com/race/` 로 오는 요청은 Worker 가 `Accept-Language` 로 302 한다.
`301` 이면 브라우저가 영구 캐시해 방문자가 언어를 되돌릴 수 없고,
`Cache-Control: no-store` 가 없으면 Cloudflare 가 첫 방문자의 언어를 전원에게 준다.

**주소 끝의 슬래시는 빼면 안 된다.** `/race/ko/` 이지 `/race/ko` 가 아니다.
도구의 내부 링크가 전부 상대 경로라, 슬래시가 없으면 브라우저가 한 단계 위를 기준으로 푼다:

```
/race/ko/ 기준   ../styles.css → /race/styles.css     ../en/ → /race/en/
/race/ko  기준   ../styles.css → /styles.css   ★깨짐   ../en/ → /en/  ★허브로 이탈
```

허브는 반대로 슬래시가 없다(`/ko`). 헌법 §「끝 슬래시는 build.format 이 결정한다」에 따라
허브는 Astro 의 `build.format: 'file'` + `trailingSlash: 'never'` 라 실제 파일이 `ko.html` 이고,
도구는 `ko/index.html` 이라 디렉터리 주소가 된다. 라우터가 `/race` → `/race/` 를 301 로
붙여주는 것도 같은 이유다 (헌법 §라우터 주석).

**로컬에서는 `race/ko/` 를 직접 연다.** 파일 더블클릭(`file://`)으로는 안 된다 —
ES 모듈이 CORS 로 막힌다. VS Code Live Server 같은 로컬 서버가 필요하다.

## SEO 에서 지킨 것

- `canonical` · `hreflang` · `og:url` 전부 `https://prelaps.com/...` 절대 URL
- 두 언어판이 hreflang 전체 목록을 **동일하게** 갖는다. 하나라도 빠지면 구글이 무시한다
- `x-default` 는 영어
- **설명 텍스트가 정적 HTML 에 있다.** 헌법이 경계하는 건 라이브러리가 아니라
  빈 `<div id="root">` 만 배포되어 구글봇이 못 읽는 것이다. 화면은 JS 가 그리되
  읽을 거리는 문서에 처음부터 있어야 한다
- 자산 참조는 전부 상대 경로(`../styles.css`). 절대 경로는 도메인 루트 기준으로
  풀려서 전부 깨진다 — 도구는 루트에 있지 않다

아직 안 한 것: `404.html`, 허브 `public/robots.txt` 에 사이트맵 한 줄 추가,
허브 privacy 의 「서비스별 안내」에 `#race` 블록.

## 첫 화면이 늦게 뜨는 이유는 무게가 아니라 순서였다

받아야 하는 건 853KB 인데, 문제는 크기가 아니라 **브라우저가 사슬을 한 칸씩 따라간다**는 것이었다:

```
왕복 1   HTML  →  main.js (26KB)
왕복 2   main.js 파싱  →  three.module.min.js (365KB) + src 모듈 10개
왕복 3   three.module.min.js 파싱  →  three.core.min.js (385KB)
```

**제일 큰 파일이 맨 마지막에 시작한다.** 365KB 를 다 받아서 파싱해야 그 안의 import 가
보이기 때문이다. 그래서 `<head>` 에 `modulepreload` 로 셋을 미리 알려준다 — 브라우저가
사슬을 기다리지 않고 동시에 받는다. 캐시가 비어 있을 때만 티가 나므로 「간혹 늦게 뜬다」로 느껴진다.

자바스크립트 계산은 문제가 아니었다 (합쳐서 100ms 안쪽):

```
three.js 파싱·실행   47 ms
배경(하늘·구름·나무 900)  18 ms
트랙 도형            19 ms
캐릭터 4명           13 ms
```

기다리는 동안에는 무대에 「불러오는 중…」이 뜬다. 캔버스는 불투명이라 만들어지는 즉시
덮으므로 따로 지울 필요가 없다 — 기다림의 대부분이 모듈을 받는 동안이고, 그게 이 글자가 나오는 때다.

## three.js 를 저장소에 넣어둔 이유

CDN 을 부르면 런타임 외부 의존이 생긴다. `vendor/` 에 두면 배포가 정적 파일 복사로 끝난다.
`three.module.min.js` 가 옆의 `three.core.min.js` 를 상대 경로로 import 하므로 **둘 다 필요하다.**

빌드 도구는 없다. `<script type="module">` 로 브라우저가 직접 읽는다.

## 트랙

실제 육상 경기장과 같은 오벌 — 직선 2400, 안쪽 반지름 1300, 레인 폭 85, 여덟 레인.
레인 폭은 캐릭터 몸통 너비(57)의 1.5 배로 잡았다. 좁으면 서로 붙어 보인다.
`src/track.js` 가 진행률(0~1)을 좌표와 진행 방향으로 바꿔 준다. 화면과 무관해서
`node` 로 검증할 수 있고, 경로가 이어지는 것과 여덟 레인이 결승선에서 만나는 것을 확인했다.

**출발선을 어긋내지 않고 진행률로 잰다.** 바깥 레인이 한 바퀴 더 긴 문제를 푸는 방법이 둘인데:

| | 출발선 어긋내기 | 진행률로 재기 (택함) |
|---|---|---|
| 달리는 거리 | 모두 같다 | 바깥이 20% 길다 |
| 출발 그림 | 흩어진다 | 한 줄 |
| 순위 읽기 | 안 보인다 — 바깥이 늘 앞서 있다 | 앞선 사람이 앞에 보인다 |

처음에 어긋내기로 만들었더니 출발이 정신없고 누가 앞선 건지 읽히지 않았다.
뽑기 도구에서는 「한눈에 보이는 것」이 물리적 공정성보다 중요해서 바꿨다.
속도 차이는 반지름 대비 레인 폭이 정한다. 8레인이 29%, 12레인이 45% 다.

### 「바깥이 계속 이기는 것 같다」 — 사실이 아니고, 그럼에도 진짜 문제다

레인은 승부에 **아무 영향도 주지 않는다.** `race.js` 는 레인이라는 말을 알지도 못하고
(`grep lane src/race.js` → 0건), 가중치를 전부 같게 두고 8만 판을 돌려도
레인별 우승률이 12.4~12.6% 로 고르다 (χ² = 4.5, 자유도 7, 임계 14.07).

그런데도 그렇게 느껴지는 이유는 둘 다 **보이는 것** 쪽이다.

```
바깥 레인이 안쪽보다 빨리 움직이는 정도    4명 12%  ·  8명 29%  ·  12명 45%
「옆에서」 시점에서 화면에 크게 보이는 정도  4명 +21%  ·  8명 +57%  ·  12명 +105%
```

크게 보이는 쪽이 더 크다. 바깥 레인이 카메라에 가깝기 때문인데, **카메라를 높이면 준다** —
8명 기준 pitch 13°에서 +57%, 45°에서 +34%, 62°에서 +20%. 사람 수를 줄이는 것도 그만큼 듣는다
(그래서 기본이 넷이다).

### 어긋내기는 만들어 봤다가 지웠다

실제 육상처럼 바깥 레인이 앞에서 출발해 **모두 똑같은 거리**를 달리는 모드를 구현했었다.
켜면 속도 차이가 정확히 0% 가 된다. 그런데 **승부는 이미 가중치 추첨으로 정해져 있고
레이스는 그 결과를 보여주는 연출일 뿐이라, 물리적 거리를 맞춰서 얻는 게 없다.**
반대로 잃는 건 컸다:

```
                    거리 차이   화면에 담긴 주자   전원이 다 보인 프레임
진행률로 재기 1바퀴      29%          92%             63%
같은 거리   1바퀴        0%          81%             20%
진행률로 재기 3바퀴      29%          90%             55%
같은 거리   3바퀴        0%          57%             18%
```

출발선이 흩어지는 폭이 1바퀴에 3165, 3바퀴에 5508 이라 세 바퀴짜리 판에서는
주자들이 트랙 전체에 흩어진 채 출발했고, 바깥 레인은 자기 레인 기준으로 온전한 바퀴 수를
돌지도 않았다 (3바퀴 판에서 2.33바퀴). **뽑기 도구에서는 「한눈에 보이는 것」이
물리적 공정성보다 중요하다** — 애초에 오벌 + 진행률 방식을 고른 이유와 같다.

느낌을 줄이고 싶으면 손댈 곳은 카메라다. 사람 수를 줄이거나(넷이면 +21%),
「옆에서」 샷의 각도를 올리면 된다(45°에서 +34%, 62°에서 +20%).

### 진행률을 길이 비율로 나누면 안 된다

**「같은 진행률이면 한 줄에 선다」가 오랫동안 사실이 아니었다.** `f × perimeter(r)` 로
위치를 잡았는데, 직선은 어느 레인이나 4800 으로 같고 곡선만 길어서 **한 바퀴 중 직선이
차지하는 비율이 레인마다 다르다** — 레인 0 은 37.0%, 레인 7 은 28.7%. 그래서 같은
진행률인데도 직선 위에서는 바깥 레인이 앞서 있었다. 앞 직선 구간만 놓고 재보니:

```
예전 (길이 비율)   이웃한 등수의 26.4% 가 눈으로는 뒤집혀 보임, 최대 캐릭터 1.4배
지금 (구간별)      0.00%
```

이 트랙을 이렇게 만든 이유가 「앞선 사람이 앞에 보인다」인데 그게 안 되고 있었던 것이다.

지금은 오벌을 직선·곡선 네 도막으로 쪼개고 **각 도막이 차지하는 진행률 범위를 모든 레인이
똑같이 쓴다.** 도막 안에서는 기하 변수(직선은 x, 곡선은 각도)에 선형으로 맞춘다.
경계값을 가장 안쪽 레인의 길이 비율로 잡아서 **레인 0 의 움직임은 예전과 완전히 같다**
(20000점을 재서 최대 차이 2.5e-12).

**그 대신 발맞춤 식을 바꿔야 한다.** 진행률당 거리가 더 이상 일정하지 않다 —
바깥 레인은 직선에서 느리고 곡선에서 빠르다. 레인 7 은 진행률당 12968~18904 로 움직이는데
한 바퀴 평균은 16707 이라, 그 평균을 곱하면 **-22% ~ +13% 만큼 발이 미끄러진다.**
그래서 지금은 「진행률 차이 × 레인 길이」가 아니라 **좌표에서 직접 잰다.**

## 발맞춤

**다리 속도를 따로 정하지 않는다. 몸이 실제로 나아간 거리에서 역산한다.**
이게 「달리는 느낌」의 거의 전부다.

처음에는 발놀림을 슬라이더로 두었는데, 재보니 **발이 11.4 배 미끄러지고 있었다** —
다리는 초당 2 걸음인데 몸은 22.6 걸음어치를 나아갔다. 사실상 문워크였다.
트랙도 너무 길어서 초당 8.1 키(우사인 볼트보다 빠름)로 달리고 있었다.

트랙을 줄이고 발을 땅에 맞물린 뒤:

처음 맞춘 뒤에도 초당 6 걸음이라 모션이 급해 보였다. 캐릭터를 170 으로 키우고
한 판을 24 초로 늘려 초당 3.3 걸음으로 내렸다. 지금:

```
한 판 24.5초 · 주자는 3.5 레인 기준 초당 606 (캐릭터 키의 3.6배)

옆으로돌기   반지름 43   초당 1.17바퀴   굴러감
전력질주     보폭 1.47키  초당 2.4걸음
행진        보폭 1.25키  초당 2.8걸음
미끄럼      보폭 2.39키  초당 1.5걸음
물구나무서기  보폭 0.76키  초당 4.6걸음   손으로 걷는다
기어가기     보폭 0.60키  초당 5.9걸음
구르기      반지름 45   초당 1.11바퀴   굴러감
둥둥        —          초당 2.4 (고정)  발이 안 닿는다
```

**주의 — 예전 표는 「한 판 24.5초」를 전제로 적혀 있었지만 화면은 그렇지 않았다.**
부스터가 늘 켜지는 버그 때문에 실제로는 18초에 끝나고 있었다. 즉 눈으로 고른 모션 값은
문서보다 **1.4배 빠른 화면에서 고른 것이다.** 2026-08-21 에 레이스를 고치면서 판 길이를
문서대로 되돌렸으니, 모션 값을 확정하기 전에 한 번 더 보고 정할 것.

### 자세가 바닥을 짚는지는 순기구학으로 잰다

주법을 새로 만들 때 눈으로 맞추면 발이 뜨거나 파고든다. `runner.js` 의 뼈대 치수를
그대로 옮겨 2D 로 풀면(회전이 전부 Z축이라 평면으로 충분하다) 한 주기 동안의 최저점이 나온다.
지금 값들 — 0 이면 딱 짚는 것이다:

```
옆으로돌기 -0.3   물구나무서기 0.0   구르기 -1.0   전력질주 -3.5
행진 -3.8   미끄럼 -7.1   둥둥 -8.4   기어가기 -10.7
```

**옆으로돌기와 물구나무서기는 이 계산 없이는 못 만들었다.**

- 물구나무서기는 손끝이 몸 좌표 83, 머리 바깥이 89 다. 머리가 늘 손보다 6 더 멀어서
  「손만 짚고 머리는 뜬다」가 이 몸으로는 불가능하다. 그래서 머리가 바닥을 스치는
  `pivot 44.5` 로 맞췄다 — 삼점 물구나무가 된다.
- 옆으로돌기는 굴러가야 해서 별이 둥글어야 한다. 다리·팔 벌림과 pivot 을 훑어
  가장 둥근 조합(다리 ±56°, 팔 ±10°, pivot 44.5, 반지름 40.9~44.5)을 골랐다.
  **머리를 빼고 세면 안 된다** — 팔다리만 보고 맞췄더니 안 접히는 머리가 가장 바깥(47)이라
  회전할 때마다 바닥을 5 씩 파고들었다. 구르기가 `r 45` 인 이유도 같다.
- 눈대중으로 넣었던 `r 40` 은 실제 반지름이 48 이라 4% 미끄러지고 있었다.

`advance()` 에 캐릭터의 월드 배율을 넘겨야 한다. 뼈대 치수가 로컬 단위라
안 넘기면 키를 키울수록 다시 미끄러진다 — 실제로 그 버그가 있었다.

주법마다 `step`(한 걸음에 나아가는 거리)만 적고 걸음 수는 계산된다.
`lock: 'roll'` 은 굴러가기(회전 = 거리 ÷ 반지름), `'free'` 는 발이 안 닿는 둥둥.
다리 각도만으로 보폭을 계산하면 실제보다 짧아서 체공 보정(`FLIGHT = 1.8`)을 얹었다.

## 가중치 — 결과를 먼저 뽑고 레이스를 연출한다

**2026-08-21 에 구조를 뒤집었다.** 예전에는 부스터를 굴려서 먼저 들어온 사람이 승자였는데,
뽑기 도구로는 틀린 구조다. 두 가지가 겹쳐 있었다.

- 부스터가 곱연산이라 개수가 복리로 불어났다. 4000회 실측에서 가중치 3 이 기대 25% 대신
  **67.4%** 를 이겼다.
- 발동 확률식 `boostChance × rerollEvery × urgency` 가 `0.012 × 700 × 0.3 = 2.52` 로
  **1을 넘었다.** 부스터를 가진 사람은 리롤마다 무조건 켠 것이다. 그래서 한 판이
  문서에 적힌 24.5초가 아니라 실제로는 **18초**에 끝나고 있었다. 숫자를 조율해서 고칠 수 없다.

지금은 순서가 반대다.

1. **가중치대로 순위 전체를 추첨한다** (Plackett–Luce — 남은 후보에서 가중 추첨을 반복).
   1등 확률이 정확히 `w / Σw` 가 된다.
2. **등수대로 도착 시각을 준다.** 간격 0.2~0.6초라 화면에서는 사진 판독감이 난다.
3. **제멋대로 흔들리는 속도 곡선을 만들고, 자기 도착 시각에 딱 1 이 되도록 나눈다.**
   곡선이 단조 증가라 중간에는 순위가 뒤집히고 역전이 나지만, 끝에는 반드시 추첨 결과대로 들어온다.

부스터는 이제 확률이 아니라 **연출**이다. 가중치가 높으면 부스터를 더 많이 쓰는 그림은
그대로 남지만 승부를 바꾸지 않는다 — 정규화가 흡수한다.

**부스터는 반드시 전부, 그리고 하나씩 따로 터진다.** 구간을 개수만큼 쪼개 한 칸에 하나씩
둔다. 그냥 뽑았더니 6.7% 가 앞엣것과 겹쳐(최소 간격 0초) 두 번이 한 번으로 보였는데,
가중치 = 부스터 개수인 도구에서 눈에 두 개만 보이면 도구가 거짓말을 하는 것이다.
지금은 겹침 0%, 최소 간격 2.05초, 결승선을 넘겨 끝나는 것 0개, 안 쓰고 남는 것 0개다.
연출로 바꿨다고 부스터가 허깨비가 된 것도 아니다 — 켜진 동안 **1.42배** 빠르고,
한 번에 트랙의 **8%** 를 벌며, 평균 **1.64계단**을 올라온다.

40000 판 실측:

```
철수 w3   실제 25.4%   기대 25.0%
민수 w2   실제 16.8%   기대 16.7%
영희 w1   실제  8.3%   기대  8.3%
```

연출이 죽지 않았는지도 같이 쟀다 (300판):

```
1등 교체                     한 판에 11.6회
우승자가 선두로 달린 시간      46%      (100% 면 김빠진다)
결승 3초 전에 우승자가 선두    66%      (나머지 34% 는 막판 역전)
진행률이 뒷걸음질친 프레임      0
```

속도 곡선을 사인파의 합으로 잡은 덕에 **적분이 닫힌 형태로 나온다.** 그래서 진행률이
프레임 시간과 무관하다 — 4ms · 16ms · 60ms 로 돌려도 도착 순서가 같고 같은 시각의
진행률이 완전히 일치한다. 예전 수치적분은 4배속으로 돌리면 결과가 달라졌다.

### 확률 검정

1등만 맞아서는 부족하다. 세 명짜리(가중치 3:2:1)로 **순위 전체 분포**를 이론값과 대조했다.
120000판, χ² = 2.14 (자유도 5, 5% 임계 11.07) — 여섯 가지 순열이 전부 이론값에 붙는다.
1등 확률은 조합을 바꿔가며 따로 검정했다. 균등 8명 · 기본값 8명 · `[20,1,1,1]` ·
`[9,1]` · 소수 가중치 · `[100,300,600]` 전부 합격, 기대와 최대 차이 0.3%p 이내다.

**여기서 4배속 버그를 하나 잡았다.** `main.js` 가 프레임을 60ms 로 자른 뒤 배속을 곱하므로
4배속에서는 한 스텝이 240ms 다. 등수 간격이 0.18초부터라 둘이 같은 스텝에 결승선을 넘고,
그러면 `finished` 에 **레인 번호 순으로** 들어가 추첨 결과와 어긋났다 — 300판 중 24판.
지금은 같은 스텝에 들어온 사람을 도착 시각으로 정렬해서 넣고, 순위표도 `pos` 가 같을 때
도착 시각으로 가른다. dt 를 600ms 로 줘도 어긋나지 않는다.

**부스터 개수와 가중치는 떼어 놓았다.** 개수는 보여주는 값(반올림, 최대 6개)이고
가중치는 확률을 정하는 값이다. 24.5초짜리 판에 부스터 20개를 넣으면 칸이 1초도 안 되어
계속 켜진 것처럼 보이는데, 개수를 깎아도 확률은 안 변한다 — 정규화가 개수와 무관하게
도착 시각을 맞추기 때문이다. 가중치 0 은 지금 `0.0001` 로 깔려 있어 우승률이 0 이 아니라
0.005% 다. **「0 이면 아예 못 이긴다」로 할지는 이름·가중치 입력을 붙일 때 정할 일이다.**

## 카메라

**각도 규약은 실측해서 쓴다.** 예전 주석은 `yaw 0 = 바로 뒤, 90 = 옆` 이라고 되어 있었는데
**두 값이 서로 바뀌어 있었다.** 그래서 `side`(yaw 90)라는 이름의 프리셋이 실제로는
뒤통수만 보고 있었다. 실측값:

```
yaw   0 = 주자 옆(트랙 바깥쪽)    90 = 바로 뒤
    180 = 옆(인필드쪽)          270 = 정면에서 마주봄
```

의심되면 「카메라→주자」 벡터와 주자 정면이 이루는 각을 `node` 로 재보면 된다.

**1등을 쫓지 않는다.** 순위는 한 판에 열 번 넘게 바뀌고 그중 41% 는 1초도 못 버티는데,
바뀔 때마다 목표가 다른 레인으로 넘어가 캐릭터 두세 명 폭만큼 튄다(실측 평균 339, 최대 666).
그래서 「누구」가 아니라 **「어디까지 왔나」** 를 본다 — 선두 진행률을 가운데 레인(3.5) 위에
올려놓고, 무리 쪽으로 조금 당긴다(비율 0.7, 최대 320). 프레임당 최대 이동이 **666 → 27** 로
떨어졌다. 27 은 그냥 정상 주행 속도다.

**lerp 대신 크리티컬 댐프 스프링.** 예전 것은 시간상수 72ms 짜리 지수감쇠라 관성이 아예 없었다.
스프링은 속도를 들고 있어서 방향이 바뀔 때 관성이 생기고, 그러면서도 오버슛 없이 멈춘다.

**자동 연출은 컷으로 끊는다.** 육상 중계와 마블런의 문법이다 — 부드럽게 옮기지 않는다.
구간은 트랙 기하에서 나온다(앞 직선 0~0.093, 곡선 0.093~0.408, 뒤 직선 0.408~0.593, 곡선 0.593~0.908).
샷마다 최소 유지 시간이 있어서 경계에서 컷이 깜빡이지 않는다.

```
0.0s  launch  정면에서 낮게 — 달려오는 걸 본다
3.5s  inside  곡선, 인필드 쪽에서
7.2s  arc     같은 곡선 후반, 앞쪽 사선으로 낮게
10.0s side    뒤 직선, 트랙 바깥에서 나란히
14.2s sweep   둘째 곡선을 높이 잡아 판을 보여준다
18.2s press   마지막 직선 직전, 뒤에 바짝
21.6s goal    결승선 고정
24.5s winner  우승자 클로즈업
```

무리가 벌어지면 물러나고 붙으면 당긴다(배율 0.78~1.6 로 상·하한을 둔다 — 스팬에서 거리를
그대로 역산하면 발산한다). 부스터가 켜지면 화각을 40 → 48 로 밀어 속도감을 만든다.

**손으로 고르는 시점은 셋뿐이다** — 옆에서 · 위에서 · 전체. 여섯 개를 두었더니
「뒤에서」와 「구석에서」가 서로 비슷하고 「골대에서」는 자동 연출이 마지막 구간에 이미
잡아 준다. 남긴 셋은 하는 일이 다르다 — 따라붙기 · 판 읽기 · 전체 보기.
그 사이 각도는 끌어서 맞춘다.

**조작이 자동을 이긴다.** 끌면 그때부터 손이 이기고, 손을 떼고 3초 지나면 자동으로 돌아온다.
시점을 직접 고르면 자동은 아예 꺼져서 맞춰 둔 각도가 그대로 유지된다.
감도는 px 가 아니라 화면 크기 기준이다 — 예전에는 px 당 0.3도 고정이라
폰(390px)에서 화면을 다 쓸어도 117도밖에 못 돌았다. 핀치 줌과 놓은 뒤 관성도 이때 넣었다.

**결과창이 조작을 통째로 가로막고 있었다.** `.result` 에 `display: flex` 를 준 탓에
작성자 스타일이 브라우저 기본 `[hidden] { display: none }` 을 이겨서, 결과창이 **안 보이는
채로**(opacity 0) 무대 전체를 덮고 있었다. `z-index: 3` 이라 캔버스로 가야 할 드래그와 휠이
전부 거기로 빨려 들어갔다. `.result[hidden] { display: none }` 한 줄로 끝난다.

자동 연출은 스스로 움직이니 티가 안 나고, **시점을 고른 뒤에야** 「마우스가 안 먹는다」로
드러난다. 카메라 쪽 테스트는 통과하고 있었는데, `RaceCamera` 객체를 직접 두드렸을 뿐
**브라우저가 이벤트를 캔버스까지 보내주는지는 재지 않았기 때문**이다. 지금은
무대를 덮는 요소가 셋 중 하나(안 보일 때 `display:none` · `pointer-events:none` ·
실제로 조작을 받아야 하는 것)인지 확인하는 검사를 따로 둔다.

**「3초 뒤 자동 복귀」가 실제로는 안 되고 있었다.** 자동이 각도를 되찾는 코드가
샷이 바뀌는 순간에만 있어서, 끌어 놓으면 다음 컷이 올 때까지(최대 4초) 그 각도에 머물렀다.
안내 문구는 3초라고 말하는데 화면은 아니었던 것이다. 지금은 자동이 되찾는 순간
그 샷의 각도를 다시 목표로 삼는다 — 컷하지 않고 스프링으로 되돌아간다.
방금 보던 화면이 뚝 끊기면 조작을 빼앗긴 느낌이 든다.

## 배역 배치 — 결과를 아는 걸 써먹는다

**승부가 이미 정해져 있다는 게 여기서 최대 장점이 된다.** 속도 곡선을 도착 시각 기준으로
정규화하므로 중간에 무슨 일이 일어나든 결과는 안 변한다. 그래서 사고를 이야기에 맞춰
**배역처럼 배치할 수 있다** — 물리로 굴리는 레이스에서는 못 하는 일이다.

```
우승자   75% 확률로 초반(15~50%)에 미끄러진다 → 뒤처졌다가 치고 올라온다
꼴찌     75% 확률로 후반(55~88%)에 무너진다
그 밖    85% 확률로 아무 데나 한 번, 누구나 25% 확률로 하나 더
```

실측: 우승자가 초반에 미끄러진 판 87%, 꼴찌가 후반에 무너진 판 69%,
w3 우승률 24.9% (기대 25.0%) — 확률은 그대로다.

### 배역을 곧이곧대로 지키면 결과가 새어나간다

미끄러지는 데 이유가 안 보이면 고장으로 보인다. 그래서 **미끄러질 자리에 바나나 껍질을
깔아 둔다** — 추첨이 이미 끝나 있으니 언제 걸릴지도, 그때 어디쯤일지도 계산할 수 있다
(`race.progressAt()`). 그런데 웅덩이가 출발 전부터 다 보이니 **배역이 그대로 노출된다.**
처음 규칙(우승자 초반 100%, 꼴찌 막판 100%)으로 4만 판을 재보니:

```
                              고친 뒤    처음    우연이면
가장 이른 껍질의 주인이 우승자    19.0%   72.9%    12.5%
가장 늦은 껍질의 주인이 꼴찌      25.1%   79.4%    12.5%
껍질을 가진 비율 (우승/꼴찌/중간)  97/97/89%   99/100/40%
```

몇 판만 봐도 「제일 앞 껍질이 우승자」를 알아챌 수준이었다. 배역을 4분의 3만 지키고
나머지 주자에게도 트랙 전 구간에 웅덩이를 흩뿌려 신호를 묻었다. 이야기는 살아 있다 —
우승자는 여전히 87% 확률로 초반에 미끄러진다.

**껍질은 미끄러짐이 시작되는 바로 그 지점에 깐다.** 처음에 25% 지점에 깔았더니
주자가 껍질에 닿기 **181 앞에서 이미 미끄러지기 시작해** 순서가 거꾸로 보였다.
지금은 밟는 순간 시작하고, 미끄러지는 1.2초 동안 껍질을 지나 563 을 더 밀려간다.
1742개를 검사해 **전부** 껍질 위를 지나간다.

자리는 주자당 최대 두 개다 (배역 하나 + 가끔 하나 더). 모자라면 껍질 없이 미끄러지는
주자가 생기는데 그게 바로 고치려던 문제라, 자리를 인원의 두 배로 잡았다.
레인을 섞으면 껍질도 같이 옮겨야 한다 — 껍질은 레인 위에 있다.

### 껍질도 도형 파일 없이 만든다

처음엔 진흙 웅덩이(납작한 타원)였는데, 어둡고 납작해서 주황 트랙 위에서 그림자처럼
보일 위험이 있었다. 바나나 껍질은 미끄러짐의 만국 공통 기호이고 밝아서 눈에 띈다.

가운데 꼭지(눌러 놓은 구) 하나와 벌어진 껍질 세 장(눕힌 원뿔)로 조립한다.
둘 다 `InstancedMesh` 라 **몇 개가 깔리든 드로우콜은 둘**이고, 껍질 하나가 삼각형 116개다.

```
크기      71 × 68 × 17   (캐릭터 키의 42% 폭, 10% 높이)
바닥      1.3 ~ 17.8     (트랙 표면 0.5, 레인선 1.2 바로 위)
```

높이를 6 으로 뒀더니 트랙에 **4.2 파묻혀** 있었다. 눕힌 원뿔의 아랫면이 어디 오는지
재서 11.5 로 올렸다.

### 함정은 부스터와 같은 구조다

부스터가 이미 「속도 곡선 위의 봉우리」다. 함정은 **음수 봉우리**일 뿐이라
적분식도 그대로 쓴다. 다만 **속도가 0 밑으로 가면 주자가 뒷걸음질친다.**
지금 곡선이 이미 0.23 까지 내려가므로 아무 데나 파면 안 된다:

```
깊이 0.2 → 최저 0.03   위험
깊이 0.4 → 최저 -0.17  뒷걸음질
```

그래서 **속도가 높은 순간을 찾아 판다.** 2400명분을 재보니 그런 자리에서는 깊이 1.26 이상
(중앙 1.86)을 팔 수 있어서, 원하는 0.75 는 늘 나온다. 잘 나가다 걸리는 편이 더 극적이기도 하다.
자리는 열여섯 번만 찔러보고 충분하면 멈춘다 — 끝까지 최적을 찾으니 추첨 한 번이
0.59ms 였는데, 그렇게 줄여서 **0.025ms** 가 되었다 (실시간 입력이 여기에 걸려 있다).

부스터와 겹치지 않게 0.6초는 떼어 놓는다. 겹치면 서로 상쇄되어 둘 다 안 보인다.

한 번 걸리면 1.2초 동안 **32% 덜 나아간다** (최대 44%). 눈에 띄기에 충분하다.

## 부스터 효과

셋을 겹친다. 하나만 쓰면 밋밋하다.

- **속도선** — 뒤로 흘러나가 사라지는 짧은 선분들. 「빨라졌다」를 만드는 건 캐릭터가 아니라
  곁을 스쳐 지나가는 것들이다(트랙에 거리 눈금을 넣은 이유와 같다). 선분 420개를 미리
  만들어 돌려 쓴다 — 여덟 명이 동시에 켜도 232개면 된다.
- **잔상** — 지나온 자리에 몸통·머리만 반투명으로 남긴다. 「막 이동한다」는 느낌은 여기서 나온다.
  팔다리까지 복제하면 도형이 여덟 배가 되는데, 빠르게 지나가는 실루엣에서는 어차피 안 읽힌다.
- **화각과 고리** — FOV 를 밀고, 부스터 고리가 걸음에 맞춰 뛴다. 켜고 끄기만 하면 눈에 안 띈다.

선분은 알파를 못 쓰는 재질이라 **배경색 쪽으로 섞어서** 사라지게 한다. 배경이 단색이라
눈에는 페이드로 보인다.

## 캐릭터와 이름표

**생김새는 시작할 때 한 번 나눠 주고, 섞기 버튼 둘은 생김새를 건드리지 않는다.**
「자세 섞기」는 달리는 자세만, 「레인 섞기」는 서는 자리만 다시 뽑는다.
**레인은 배열 순서와 떼어 놓았다** — 색과 순위판 자리는 배열 순서를 따르고 트랙 위 자리만
`lane` 을 따른다. 레인 섞기는 달리는 중에는 막는다. 레인이 바뀌면 주자가 옆으로
순간이동하는데, 경기 중에 그러면 고장으로 보인다.

기본값은 네 명이다 — 여덟은 처음 보는 사람에게 「이만큼 넣어야 하나」로 읽힌다.
가중치를 하나만 2 로 둔 건 부스터가 뭔지 한 판만 봐도 알게 하려는 것이다.

생김새까지 같이 바뀌면 누가 누구였는지 매번 다시 익혀야 한다. 머리 모양과 체형은
종류 수만큼 돌려 가며 나눠 주므로 같은 모양이 몰리지 않는다 —
뽑기가 아니라 나눠 주기라 중복이 구조적으로 없다.

**섞을 때 캐릭터를 다시 만들지 않는다.** 캐릭터가 `spec` 객체를 그대로 들고 있고
자세와 레인을 매 프레임 거기서 읽으므로, 값만 갈아 끼우면 다음 프레임부터 적용된다.

**섞는 데 `sort(() => Math.random() - 0.5)` 를 쓰지 않는다.** 예전 코드가 그랬는데,
20만 번 돌려보니 어떤 칸은 기대값보다 **76.9%** 치우쳐 있었다 (χ² = 85674, 임계 66.3).
피셔–예이츠로 바꾸니 χ² = 57 로 합격한다. 생김새는 결과에 영향을 주지 않지만,
뽑기 도구에서 「대충 섞이는 것」을 쓰기 시작하면 어디까지가 대충인지 알 수 없어진다.

### 이름표

`src/labels.js`. 캐릭터 머리 위에 뜨고 버튼으로 끌 수 있다.

`Sprite` 를 쓴다 — 늘 카메라를 마주보기 때문에 트랙을 돌아도 글자가 눕지 않는다.
글자는 `CanvasTexture` 로 코드에서 그리므로 다운로드가 0바이트다.

**색은 테두리에만 쓰고 바탕은 어둡게 깐다.** 주자 색을 바탕에 깔면 노랑·주황 주자에서
흰 글자가 안 읽힌다 — 여덟 색 중 셋이 밝은 색이라 절반 가까이가 안 보이게 된다.

**크기는 매 프레임 카메라 거리에 비례해 키운다.** 월드 크기를 고정하면 멀리 있는 주자의
이름이 점이 되고 우승자 클로즈업에서는 화면을 덮는다. 거리에 비례시키면 원근 투영에서
화면상 크기가 일정해진다 — 실측으로 거리 450 부터 5800 까지 전부 화면 높이의 3.2% 다.

## 참가자와 레인 수

`src/entry.js` 가 이름·부스터 개수 칸을, `track.js` 의 `setLanes()` 가 레인 수를 맡는다.
**2~12명.** 레인 수가 바뀌면 트랙 도형(바닥·레인선·눈금·결승선)과 트랙 둘레 색 띠를
통째로 다시 만든다. 옛 도형은 반드시 `dispose()` 해야 한다 — 안 버리면 인원을 몇 번
바꾸는 사이에 GPU 메모리에 트랙이 열 장 쌓인다.

**상한이 12 인 이유는 속도차다.** 바깥 레인은 한 바퀴가 길어서 안쪽보다 빨리 움직인다:

```
레인    4     6     8    10    12    14    16    20
속도차 12%   21%   29%   37%   45%   54%   62%   78%
숲까지  446   361   276   191   106    21   -64  -234   ← 음수면 나무가 주자를 가린다
```

8레인 29% 는 「나란히 서 있어서 크게 안 띈다」고 받아들인 값이다. 16레인 62% 는
바깥 사람이 눈에 띄게 질주해 보이고, 게다가 카메라가 그만큼 물러나서 **숲이 주자를 가린다.**

속도차를 29% 로 유지하며 레인을 늘리려면 트랙을 키워야 한다 — 16레인이면 한 바퀴가
**2.14배**다. 같은 24.5초에 두 배를 달려야 하고, 발맞춤이 걸음 수를 자동으로 올리므로
모션을 다시 잡아야 한다. 그래서 12 에서 끊었다.

레인 수를 바꿔가며 확인한 것 (레인 2·4·8·12):

```
확률        기대와 실제가 0.4%p 안쪽으로 일치 (w3 대 나머지 w1)
카메라       최대 반지름 3190 (숲 안쪽 끝 3900 아래)
나무 가림    전부 0프레임
```

`LANES` 는 `let` 이다. ES 모듈은 바인딩이 살아 있어서 `import { LANES }` 로 가져간
쪽도 바뀐 값을 그대로 본다 — 다만 **모듈 최상단에서 미리 계산해 둔 값은 안 따라온다.**
카메라의 초점 레인과 배경의 트랙 바깥 반지름이 그래서 함수로 바뀌었다.

**기본 이름은 HTML 에서 읽는다** (`#entries` 의 `data-names`). 언어판마다 다른 글자는
이미 전부 거기에 있다 — `data-ph`(빈 칸 안내), `data-fallback`(이름을 비웠을 때),
`data-running`(상태 줄), `data-word`(바퀴). 코드에 한국어 이름을 박아 두면 영어판에서 튄다.

입력값은 정리해서 되돌려 쓴다. 빈 이름은 「주자 N」, 빈 가중치는 1, 음수는 0,
99 초과는 99 로 자른다. **아무것도 저장하지 않는다** — 페이지에 「새로 고치면 사라집니다」
라고 적어 두었으므로 localStorage 를 쓰면 그 문장이 거짓말이 된다.

### 「적용」 버튼은 없다 — 바뀐 것만 다시 만든다

비용을 재보고 지웠다. node 기준(GPU 업로드 제외):

```
캐릭터 12명 만들기        10.0 ms
트랙 도형 전체             3.6 ms
배경 색 띠 + 체크무늬       0.5 ms
레이스 추첨              0.01 ms
────────────────────────────────
인원이 바뀔 때 합계       14.1 ms   ← 60fps 한 프레임(16.7ms) 안이다
가중치·바퀴만 바뀔 때     0.01 ms
```

그래서 **무엇이 바뀌었느냐에 따라 필요한 만큼만** 다시 만든다.

| 바뀐 것 | 다시 만드는 것 |
|---|---|
| 이름 | 이름표와 순위판 글자만. 레이스는 건드리지 않는다 (160ms 미룬다) |
| 가중치 | 추첨만 다시 — 승자가 달라져야 하므로 |
| 인원 | 트랙 도형 + 캐릭터 전부 |
| 바퀴 수 | 추첨만 다시 (판 길이가 달라진다) |

이름을 고쳤다고 트랙까지 새로 만들면 글자 하나 칠 때마다 프레임이 끊긴다.
이름은 조금 미뤄서 반영한다 — 글자마다 캔버스에 이름표를 다시 그릴 이유가 없다.

## 바퀴 수

1~5바퀴, 숫자로 직접 넣는다. 위치 계산이 진행률을 나머지로 감기 때문에(`track.js` 의 `place`)
**기하는 손댈 게 없었다.** 진행률 0~1 이 「완주」이고, 거기에 바퀴 수를 곱해서 넘기면 된다.
실제로 재보니 레인 0 의 이동거리가 바퀴 수 × 한 바퀴와 **오차 0.00%** 로 맞는다.

건드려야 했던 건 셋이다.

- **판 길이.** `TUNE.seconds` 는 「한 바퀴」 기준이라 바퀴 수를 곱한다. 1·2·3바퀴가
  24.5 · 49 · 73.5초다. 73초는 뽑기로는 길어서 **입력칸 옆에 길이를 같이 보여준다** (4배속이 있다).
- **자동 연출.** 구간으로 고르는 샷은 전체 진행률이 아니라 **이번 바퀴의 어디쯤인가**를
  봐야 한다. 안 그러면 세 바퀴짜리 판에서 한 바퀴 내내 같은 샷이 나온다.
  출발 샷만 전체 기준으로 첫 바퀴 초반에 한 번 쓴다. 3바퀴 샷 순서:
  `launch → (inside → arc → side → sweep → press) × 3 → goal → winner`
- **상한.** 위치가 나머지로 정해지므로 선두와 꼴찌의 진행률 차이가 한 바퀴를 넘으면
  뒤진 사람이 앞선 사람과 **같은 자리에 겹쳐 보인다.** 실측으로 그 차이가 최대 0.157 이라
  5바퀴면 0.79 로 아직 여유가 있고 6바퀴면 0.94 로 아슬아슬하다. 그래서 5 에서 끊었다.

확률은 바퀴 수와 무관하다 (1바퀴 25.2%, 3바퀴 25.0%, 기대 25.0%).

**카메라 초점이 한동안 틀려 있었다.** 주자는 `place(레인, 진행률 × 바퀴)` 에 놓는데
카메라의 `focus()` 는 바퀴를 안 곱하고 있어서, 바퀴가 2 이상이면 트랙의 엉뚱한 데를
보고 있었다 (최대 4576 어긋남). 바퀴 기능을 넣을 때 같이 놓친 것이다.

## 순위판과 결과창

`src/hud.js`. 무대 위에 겹치는 **HTML** 이다 — 3D 안에 그리지 않는다.
글자가 또렷하고(캔버스 텍스처는 확대하면 뭉갠다), 도형도 드로우콜도 하나 안 늘고,
글꼴·줄바꿈을 브라우저가 알아서 한다. 곁판에 있던 순위 목록은 이걸로 대체해서 지웠다 —
같은 걸 두 군데 두면 한쪽이 반드시 뒤처진다.

**매 프레임 `innerHTML` 을 다시 쓰지 않는다.** 예전 곁판이 그러고 있었다 —
초당 60번 여덟 줄을 새로 파싱하는 짓이다. 지금은 줄을 한 번 만들어 두고 바뀐 값만 쓴다.
가짜 DOM 으로 쓰기 횟수를 세어 봤다:

```
값이 안 바뀐 프레임         DOM 쓰기 0번
한 판(1745프레임) 전체      392번 = 프레임당 0.22번
예전 방식                  프레임당 최소 8번 + innerHTML 파싱
```

**순위가 바뀌면 줄을 옮기지 않고 `transform: translateY` 만 바꾼다.** DOM 순서가 그대로라
브라우저가 레이아웃을 다시 계산하지 않고, CSS transition 이 붙어서 순위표가 미끄러지듯
자리를 바꾼다. 줄 높이(23px)는 `styles.css` 의 `.hud-row` 와 `hud.js` 의 `ROW` 가 같아야 한다.

결과창은 **모두 들어온 뒤**에 뜬다. 1등이 끊자마자 띄우면 나머지가 들어오는 걸 가리는데,
그 사이 2.6초 동안 카메라는 이미 우승자 클로즈업을 잡고 있다. 버튼 글자는 이미 있는
「다시」 버튼에서 가져온다 — 언어판마다 따로 관리하지 않으려고.

## 배경

`src/scenery.js` 가 트랙 바깥을 만든다. 트랙 자체(바닥·레인선·결승선·눈금)는 `main.js` 가
그대로 그린다 — 잘 돌아가는 걸 굳이 옮기지 않았다.

밝은 야외 공원이다. 화사한 벽돌빛 트랙, 밝은 잔디, 그라디언트 하늘, 구름,
그리고 경기장을 빙 두르는 숲. 처음에는 야간 경기장(관중석·조명탑)으로 만들었다가
그쪽이 아니라고 해서 갈아엎었다. 옛 버전은 `.backup-race-20260821/` 에 있다.

### 나무를 어디에 심을 수 있나 — 이게 이 파일의 전부다

아무 데나 심으면 카메라와 주자 사이에 들어와 경기를 가린다. 그래서 먼저 쟀다.
「전체」 시점을 빼면 카메라는 **트랙 중심선 기준 반지름 628 ~ 3009** 안에만 머문다.
추격 카메라가 가장 멀어지는 경우가 「옆에서」 샷이 최대로 줌아웃했을 때로
`1597 + 1300 × 1.6 × cos13° = 3623` 이다. 그래서 **숲의 안쪽 끝은 3900**.

인필드 한가운데에도 심어 봤다가 뺐다. 「골대에서」 시점이 결승선에 낮게(높이 322) 붙어
반대편을 건너다보기 때문에 **1600프레임 중 1031프레임을 가렸다.** 인필드는 비워 두는 게 맞다.

검사는 **반드시 3D 로 해야 한다.** 처음에 평면에서 재봤더니 위에서 내려다보는 시점
(전체·위에서)이 전부 거짓 양성으로 잡혔다 — 시선이 나무 위를 지나가는데 평면으로는
그게 안 보인다. 나무를 원기둥으로 놓고 카메라→주자 선분을 40등분해 훑으면 제대로 나온다.
지금은 자동 연출·여섯 프리셋·강제 최대 줌아웃까지 **전부 0프레임**이다.

### 비용

```
드로우콜 9   삼각형 39,428   나무 900그루 + 구름 46   그림자 던지는 도형 0
다운로드 851KB → 865KB (+14KB, +1.6%)
        (비교) 캐릭터 8명이 드로우콜 144, 삼각형 29,888
```

나무 900그루가 캐릭터 한 명보다 싸다. 이유가 셋이다.

- **이미지 파일을 한 장도 안 쓴다.** 결승선 체크무늬는 `CanvasTexture` 로 코드에서 그린다 —
  다운로드 0바이트. 이미지 한 장이면 보통 100~500KB 인데 우리 코드 전체가 66KB 다.
- **같은 도형은 `InstancedMesh` 로 찍는다.** 나무 900그루가 기둥·침엽수잎·활엽수잎
  **드로우콜 세 개**다. 개별 메시로 만들면 1800개가 되어 폰에서 죽는다.
- **배경에는 그림자를 켜지 않는다.** 그림자를 던지는 물체는 한 프레임에 두 번 그려진다.

### 안개

`near = 보는거리 × 1.2`, `far = 그 + fogSpan`. 보는 거리에 물려 두면 시점마다 다시 잡을
필요가 없다 — 고정값으로 두었더니 「전체」 시점에서 카메라가 5800 물러날 때 경기장이
통째로 지워졌다.

`fogSpan` 은 분위기마다 다르다. 밤에는 좁아야(11000쯤) 어둠에 잠기는 맛이 나는데,
낮에 그 값을 쓰면 3900 밖의 숲이 하늘색에 절반 넘게 묻힌다. 낮은 26000 이다:

```
           주자   건너편 숲 앞줄   뒷줄
자동 연출    0%        16%        33%
옆에서       0%        20%        37%
골대에서     0%         9%        27%
전체        0%         4%        21%
```

주자는 늘 또렷하고, 숲은 앞줄과 뒷줄이 갈려 원근이 생긴다.

**분위기는 `MOODS` 숫자 묶음 하나가 정한다.** `main.js` 의 `const M = MOODS.day` 를
`MOODS.sunset` 으로 바꾸면 노을이 된다. 하늘·트랙·잔디·잎·레인선·속도선 색이 한꺼번에 따라간다.
속도선은 밝은 배경에서 흰색으로 밝히면 안 보여서 **반대로 어둡게** 간다(`mood.streak`).

   `Accept-Language` 로 302 하는 Worker 라우트.

모션 슬라이더는 2026-08-21 에 지웠다. 값은 확정되었고 `main.js` 의 `opt` 한 곳에만 있다.
**다시 만질 일이 생기면 슬라이더를 되살리지 말고 그 숫자를 고칠 것** — 양쪽에 값을 두었을 때
HTML 의 옛 값(키 110)이 코드 값(170)을 덮어써서 캐릭터가 작은 채로 다리만 1.5배 빨리
움직인 적이 있다.

정해지지 않은 것: 도구 슬러그 `race` 는 내가 정한 값이고 확인을 안 받았다.
가중치 0 은 지금 우승률이 0 이 아니라 0.005% 다 (`0.0001` 로 깔려 있어서).
「0 이면 아예 못 이긴다」로 할지 정할 것.

## 결정 기록

왜 이렇게 되어 있는지 — 되돌리려다 같은 자리에 다시 빠지지 않도록.

| 정한 것 | 왜 |
|---|---|
| 도구 루트를 비움 | 루트에 한 언어를 두면 그게 canonical 이 된다. mojibake 의 실수를 안 따라감 |
| three.js 를 vendor/ 에 | CDN 은 런타임 외부 의존. 빌드 도구는 여전히 없음 |
| 설명을 정적 HTML 에 | 헌법이 막는 건 라이브러리가 아니라 빈 `<div id="root">` |
| 오벌 트랙 | 직선에서는 뒤처진 주자가 화면 밖으로 사라진다 |
| 출발선을 안 어긋냄 | 어긋내면 누가 앞선 건지 눈으로 못 읽는다. 진행률로 재고 20~29% 속도차를 받아들임 |
| 다리 속도를 이동 속도에서 역산 | 따로 정하면 반드시 어긋나고 발이 미끄러진다 |
| 기본값을 `opt` 한 곳에만 | HTML 에도 두었더니 옛 값이 코드 값을 덮어썼다 |
| 규칙·기하를 화면과 분리 | `node` 로 수천 번 돌려 검증하려고 |
| 승자를 먼저 뽑고 연출 | 부스터를 굴려서 정하면 가중치가 확률로 안 옮겨진다. 숫자 조율로는 못 고침 |
| 속도 곡선을 사인파 합으로 | 적분이 닫힌 형태라 진행률이 프레임 시간과 무관해진다 |
| 카메라가 1등이 아니라 진행률을 봄 | 1등은 한 판에 열 번 넘게 바뀌고, 바뀔 때마다 목표가 튄다 |
| 자동 연출을 컷으로 | 중계 문법이 그렇다. 부드럽게 옮기면 오히려 어색하다 |
| 조작이 자동을 이기고 3초 뒤 복귀 | 껐다 켜게 하면 아무도 안 켠다 |
| 인원 상한 12 | 16레인은 속도차 62% 에 숲이 주자를 가린다. 트랙을 키우면 모션을 다시 잡아야 함 |
| 입력은 「적용」을 눌러야 반영 | 글자마다 반영하면 레인이 바뀔 때마다 트랙을 다시 만들게 된다 |
| 아무것도 저장 안 함 | 「새로 고치면 사라집니다」라고 적어 두었다 |
| 배경에 이미지 텍스처를 안 씀 | 한 장이 100~500KB. 코드로 그리면 0바이트 |
| 관중을 InstancedMesh 로 | 개별 메시면 드로우콜 2600개. 이게 진짜 비용이다 |
| 안개를 보는 거리에 물림 | 고정하면 「전체」 시점에서 경기장이 통째로 지워진다 |
